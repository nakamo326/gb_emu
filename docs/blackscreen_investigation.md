# Teensy ディスプレイ・ブラックアウト調査記録

最終更新: 2026-07-31

SAI1 オーディオ有効時に ST7789 がランダムなタイミングで真っ黒 (DISPOFF) になる不具合の
調査記録と対策手順。**0 ベースで再調査し、原因を電気的結合と確定**した。

---

## 1. 結論（確定）

SAI1 の**電気的活動（特に BCLK 1.4MHz の高 dV/dt エッジ）が DC 線へ容量結合**し、
**`cmd()` → `data_pio()` の DC 遷移直後の整定期間**に DC を low 側へ引き戻す。その瞬間に
流れていたのが `set_window()` の CASET パラメータ `0x28` で、これが DISPOFF コマンドとして
latch されていた。

**危険窓は DC の遷移直後だけ**であり、バルク DMA 転送中（DC を high で保持している ~11ms）では
起きていない（§4.2 の CGB ROM 検証で確定）。「DC を最強・高速駆動したら悪化」（§4 表）も、
速いエッジほど未終端配線でリンギングが大きくなる＝整定が乱れる、として整合する。

**対策: 危険窓に 0x28 を流さない。これで解消した（実機確認済）。**

1. **露出面側**: CASET を毎フレーム送らず、通常フレームは `RAMWR` のみ … **実装済・実機で解消確認**（§5）
2. **源側**: SAI 出力ピンのエッジを鈍化（駆動最弱・スルーレート遅） … **実装済** (commit 2f4610a)
3. **受け側**: DC 線に RC ローパス … **不要になった**（再発時の保険として §6 に手順を残す）

> **更新 (2026-07-31)**: 当初「ファームウェア単独では解決不可」と結論していたが誤りだった。
> §3.1 の解析で DMG ROM の 0x28 露出が **CASET の 1 バイト/フレームだけ**と判明し、
> それを消すことでソフトのみで解消した。ハードウェア対策（RC）は未実施のまま。

---

## 2. 症状

- SAI1 オーディオを有効化すると、起動直後〜数分のランダムなタイミングで画面が真っ黒になる
- 黒化後も**音は継続**し、パニック・クラッシュはない。`draw()` は毎フレーム正常に呼ばれ FPS 正常
- **DISPON (0x29) を送ると復帰**する → パネルは DISPOFF 状態に落ちている
- まれに未描画の余白帯に**残像**が出る（CASET/RASET パラメータの化け＝ウィンドウ誤設定。黒化と同根）
- アンプ・スピーカーの接続有無、カートリッジ回路の有無は無関係

---

## 3. 機序（なぜ 0x28 がコマンド化するか）

ST7789 は 4-wire SPI で、**バイト境界ごとに DC ピンをサンプル**する。DC=low ならコマンド、
high ならデータ。DISPOFF が latch されるには、送出の瞬間に DC=low かつバイト値 0x28 が必要。

- `set_window()` の CASET パラメータは `[0x00, 0x28, 0x00, 0xC7]`。2 バイト目 0x28 は
  `x0 = (WIDTH 240 − GB 160) / 2 = 40 = 0x28`（余白オフセットそのもの）。
- バルク転送中の **ピクセルバイトに散在する 0x28** も同じ経路でコマンド化しうる。DC は本来この間
  high 固定だが、**結合グリッチで一瞬 low に見える瞬間に 0x28 が流れるとコマンド化**する。

> **訂正 (2026-07-31)**: 当初はこのピクセル側の露出が支配的と考えていたが、§4.1 の通り
> **DMG ROM ではピクセルデータに 0x28 は 1 個も現れない**。DMG では露出は CASET の 1 バイト/フレームのみ。

### 3.1 DMG ROM の送出バイト集合（`SUPERDONKEYKONG .gb` で判明）

`SUPERDONKEYKONG .gb` はヘッダ 0x143 = 0x20 の **DMG ROM**（0x146=0x03 SGB 対応、MBC1+RAM+BATT）。
DMG モードでは `core/src/ppu.rs` の `DMG_PALETTE` 4 色しか出力されず、
`rgb555_to_rgb565()` を通した後の送出バイトは次の 8 種類に限られる:

| 色 | RGB555 | RGB565 | 送出バイト |
|---|---|---|---|
| 0 | E0F8D0 相当 | 0xE7FA | E7, FA |
| 1 | 88C070 相当 | 0x8E2E | 8E, 2E |
| 2 | 346856 相当 | 0x334A | 33, 4A |
| 3 | 0E1820 相当 | 0x08C4 | 08, C4 |

**0x28 は含まれない**。よって DMG ROM では、1 フレーム 46080 バイトのピクセル転送は
DISPOFF 誤発火の経路になりえない（オーバーレイ PIO 描画は `display/mod.rs` で無効化済みのため
そこからの 0x28 もない）。**残る 0x28 は `set_window()` の CASET パラメータ 1 バイト/フレームだけ**。

副次的な知見: この 8 バイトのうち DC グリッチでコマンド化すると意味を持つのは
**0x2E (RAMRD)**、**0x33 (VSCRDEF)**、0x08 (RDDMADCTL) のみ。DISPOFF にはならないが、
**0x33 = VSCRDEF は「余白帯の残像」症状を説明しうる**（縦スクロール定義の化け）。

## 4. 確定した切り分け（すべて実機・1 flash 1 変数）

| 検証 | 結果 | 意味 |
|---|---|---|
| **SAI を完全停止** (TE=0, 割り込み unmask なし) | **表示が完全安定** | SAI が必要条件（決定打） |
| 無音テスト (push で 0 固定 → データ線 pin7 静的 low、BCLK は回る) | 黒化継続 | データ線結合・スピーカー電流は無実。アグレッサは BCLK/クロック系 |
| SPI クロック 33MHz→11MHz | 効果なし | victim 側 SPI エッジ速度/タイミングではない |
| DMA 補充を 8 ワードバースト化 (FIFO アンダーラン耐性 8 倍) | 頻度不変 | TX FIFO アンダーランではない |
| finalize の BUSY 待ち後に 50µs settle | 効果なし | 「境界で遅延ワード着地」ではない |
| DC(GPIO2) トグル後に GPIO2 DR read-back | 効果なし | DC posted write の順序問題ではない |
| **SAI 出力ピンをエッジ鈍化** (DSE=1・遅スルー) | **部分改善（安定方向）** | 容量結合が主因の一部と確定（源側対策・採用） |
| DC を最強・高速駆動 (0xF9) | **悪化** | 長い未終端配線で速いエッジが反射/リンギング。DC は速くするな＝遅く/フィルタが正解 |

### 4.1 再現 ROM の確定と、そこから導かれる露出面

`SUPERDONKEYKONG .gb` で**安定して黒化する**ことが判明（2026-07-31）。ランダム待ちが不要になり、
1 flash 1 変数の検証が現実的な時間で回せるようになった。

同時に、この ROM が DMG であることから §3.1 の解析が成立し、露出面が
**CASET パラメータの 1 バイト/フレーム**まで絞り込まれた。ROM 依存性は「絵の中身」では説明できず、
**その 1 バイトを送出する瞬間と SAI BCLK / ISR の位相関係**（ROM ごとのフレームペーシング差）で
説明するのが自然。数分単位のランダム発生も位相ドリフトと整合する。

### 4.2 危険窓は DC 遷移直後だけ（CGB ROM 検証・決定打）

§5 の対策（CASET を毎フレーム送らない）を入れた状態で **CGB ROM も正常動作**することを確認した
（2026-07-31）。CGB ROM のピクセルデータには 0x28 が普通に含まれるため、これは

> **DC を high で保持したままのバルク DMA 転送中（1 フレーム ~11ms）には、DISPOFF を latch させる
> ようなグリッチは発生していない**

ことを意味する。もし転送中の任意タイミングで結合グリッチが DC を落としうるなら、CGB ROM は
対策後も黒化するはずだが、しない。

したがって危険窓は **`cmd()` で DC を low にし `data_pio()` で high に戻す、その遷移直後の整定期間**に
限定される。この結論は §4 表の「DC を最強・高速駆動 → 悪化」（速いエッジ＝リンギング増大）とも整合し、
「SAI 停止で完全安定」（整定を乱すノイズ源が消える）とも矛盾しない。

補足: imxrt-hal の `write()` は末尾 `flush()`（`!BUSY && FIFO empty` 待ち）で完全シフト待ちのため、
PIO コマンド送出の data→cmd race は存在しない。黒化時 LPSPI SR の TEF/REF=0（SPI エラーなし）。

## 5. ソフト対策: CASET を毎フレーム送らない（実装済・解消確認）

§3.1 で露出面が「CASET パラメータの 0x28、1 バイト/フレーム」に絞られたため、
**その 1 バイトの送出自体をやめる**のが最小かつ根本的な対策になる。

描画ウィンドウは毎フレーム同一なのに、`draw()` は毎回 `set_window()`（CASET/RASET/RAMWR）を
送り直していた。ST7789 は **RAMWR を再発行すればアドレスポインタがウィンドウ先頭に戻る**ため、
ウィンドウ設定は初回 1 回で足りる。

実装（`teensy/src/display/mod.rs`）:

- `DmaDisplay` に `window_set: bool` を追加。
- `set_window()` 成功時に `true`、`set_rect()` / `clear_screen()`（＝ウィンドウを変える経路）で `false`。
- `draw()` は `begin_frame_window()` を呼び、`window_set` なら **`cmd(RAMWR)` のみ**を送る。

これで 0x28 の送出は起動時の 1 回だけになり、毎フレームのコマンド系トラフィックも 12 バイト → 1 バイトに減る。

### 実機結果（2026-07-31）

- `SUPERDONKEYKONG .gb`（従来は安定再現）で **黒化が解消**。
- **CGB ROM も正常動作**（→ §4.2 の決定打）。

これで機序は「0x28 データが DC グリッチでコマンド化」で確定し、**ソフトのみで解決**した。
§6 の DC RC ローパスは実施不要。

### 残るリスク（許容範囲）

- `cmd(RAMWR)` の DC low→high 遷移は毎フレーム残るが、その直後に流れるのはピクセルデータであり、
  0x28 が来ても §4.2 の通り DMA 区間では latch されていない。
- 逆に DC が high 側へ化けて `RAMWR` がデータ扱いされる可能性はあるが、症状は 1 ピクセルの乱れ程度。
- オーバーレイ (`draw_text`) を再有効化すると `set_rect` で CASET が復活する。その際は
  x 座標に 0x28（=40）が現れない配置にすること（現状 `OVERLAY_X=4`, セル幅 12 → 4 文字目が x0=40）。

## 6. 対策手順: DC 線の RC ローパス（受け側）— **未実施・保険**

> §5 で解消したため**実施不要**。再発した場合や、より強い耐性が欲しい場合の手順として残す。

DC を速くすると悪化した実測結果は、**DC 線は「遅く・鈍らせる」のが正解**であることを示す。
外付けコンデンサでの RC ローパスは、駆動強度いじりでは作れない真のフィルタになる。

### 原理

DC は毎フレーム数回しか変化せず、`cmd()` で DC を切り替えてから最初の SCK エッジまで 1µs 以上の
余裕がある。一方、結合グリッチは幅数十 ns。τ ≈ 100〜200ns の RC ローパスなら、**描画に影響せず
MHz のグリッチだけ鈍らせて 0x28 の誤コマンド化を防ぐ**。

### 部品

- 抵抗 **330Ω** ×1（直列）
- セラミックコンデンサ **470pF** ×1（DC→GND）
- τ = 330Ω × 470pF ≈ 155ns

代替値（τ を 100〜200ns に保てば可）:

| 抵抗 | コンデンサ | τ |
|---|---|---|
| 330Ω | 470pF | 155ns |
| 470Ω | 330pF | 155ns |
| 1kΩ | 150pF | 150ns |
| 220Ω | 680pF | 150ns |

### 配線

抵抗はできるだけ**パネル寄り**、コンデンサは**パネルの DC ピン直近**、GND はパネル GND へ最短で。

```
Teensy pin9 (DC) ──[ 330Ω ]──┬────── ST7789 DC ピン
                              │
                          [ 470pF ]
                              │
                        パネル側 GND
```

### 手順（ブレッドボード）

1. 電源を切る。
2. DC ジャンパを一旦外し、間に列を 1 つ挟む: `pin9 → 列A`、`列A-列B` 間に 330Ω を直列に挿す、
   `列B → パネル DC`。
3. `列B`（パネル DC 側）から GND レールへ 470pF を渡す。
4. その GND レールがパネル GND と最短で共通になっていることを確認する。
5. 書き込み（`make flash`）して確認:
   - **描画が正常か**（RC が大きすぎるとコマンドが化けて白画面/描画乱れ。その場合は R か C を下げて τ を縮める）。
   - **黒化が消えたか**（まだ残るなら C を 1nF 程度まで増やして τ を伸ばす。増やしすぎは描画破壊に注意）。

### 調整の指針

- 描画が壊れる → τ が大きすぎ。R/C を下げる。
- 黒化が残る → τ が小さすぎ。C を少し上げる。
- 100〜200ns 付近で「描画正常かつ黒化消失」の窓を探る。

## 7. 補助対策（効果を上乗せしたい場合）

- **BCLK(pin26) 線を DC/SPI クラスタから物理的に隔離**（束ねない・間に GND 線・短く）。最も強い
  アグレッサを遠ざける。
- **表示モジュール VCC-GND 直近にデカップリング**（0.1µF＋10µF）。SAI 起動時のリプルを抑える。
- 必要なら **CS(pin10) にも同様の RC**。CS グリッチは転送のバイト同期を乱しうる。
- 共通 GND のスター結線・短く太く。

---

## 8. フォールバック（保険）

物理対策で発生頻度を十分下げたうえで、万一の発生を 1 フレームで自動復帰させたい場合は、毎フレーム
描画前に DISPON(0x29) を送る手がある。過去に「ちらつき」と感じたのは DISPON 自体ではなく、
**バグ発生 → 次フレームで復帰、の 1 フレーム黒フラッシュ**。発生自体が稀になれば実用上ほぼ気に
ならない安全網になる。このモジュールは MISO 未配線のためパネル状態の読み戻し（条件付き DISPON）は不可。

## 9. 技術メモ（レジスタ / パッドアドレス）

- **IOMUXC** base = 0x401F_8000。SW_PAD_CTL のビット: SRE[0], DSE[5:3], SPEED[7:6], PKE[12]。
  既定値 0x10B0（DSE=6, SPEED=2）。エッジ鈍化は 0x0008（DSE=1, SPEED=0, SRE=遅）。
  `sai::prepare` は mux/daisy のみ設定し pad ctl は触らないため、split 後に直接書けば有効。
- **SW_PAD_CTL アドレス（imxrt1060）**:
  BCLK=GPIO_AD_B1_14=0x401F_8324, LRCLK=GPIO_AD_B1_15=0x401F_8328,
  DATA=GPIO_B1_01=0x401F_8370, DC=GPIO_B0_11=0x401F_8358,
  CS=GPIO_B0_00=0x401F_832C, SCK=GPIO_B0_03=0x401F_8338。
- **LPSPI4** base=0x403A_0000（TCR=+0x60, TDR=+0x64, SR=+0x14, DER=+0x1C, FCR=+0x58,
  CCR=+0x40, CR=+0x10）。SPI 33MHz は SCKDIV=2（132/(2+2)）、main.rs で CCR 直書き。
- **GPIO2** base=0x401B_C000（DR=+0x00）。DC=pin9=GPIO_B0_11=GPIO2[11]（slow GPIO）。
- LCD は eDMA dma[0]、SAI は割り込み駆動。

## 10. ステータス

**2026-07-31: 解決。** ソフトのみで黒化は解消した。

- **再現 ROM**: `roms/SUPERDONKEYKONG .gb`（DMG）で安定再現していた。回帰確認にはこれを使う。
- **露出面側対策（CASET を毎フレーム送らない）**: 実装済。**DMG・CGB とも黒化解消を実機確認**（§5）。
- **源側対策（SAI エッジ鈍化）**: master 取り込み済 (commit 2f4610a)。併用中。
- **受け側対策（DC RC ローパス）**: **未実施・不要**。再発時の保険として §6 に手順を残す。

今後 SPI コマンド/パラメータを増やす際は、**DC 遷移直後に危険なコマンド値
（0x28 DISPOFF / 0x10 SLPIN 等）をデータとして流さない**ことを設計上のルールとする。
